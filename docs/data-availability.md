# 数据可用范围

分钟行情能追溯多远由上游接口决定。把 `--start` 写得更早，只会扩大请求范围，不会让上游生成已经不再提供的历史数据。

本页同时记录项目规则和一份 2026-08-25 的现场观测。现场数据用于帮助判断上游行为变化，不代表服务商承诺的固定历史边界。

## 当前规则

| 周期 | 默认数据源顺序 | 主要限制 |
| --- | --- | --- |
| `1` 分钟 | AKShare → 东方财富 curl | 通常只有最近 5 个交易日，新浪不支持 1 分钟 |
| `5/15/30/60` 分钟 | AKShare → 东方财富 curl → 新浪 curl | 历史范围由各上游实际返回决定，新浪没有成交额 |

默认 `FallbackMinuteProvider` 在以下情况继续尝试下一层数据源：

- AKShare 抛出异常
- AKShare 返回空表
- 东方财富 curl 请求失败
- `5/15/30/60` 分钟下，东方财富没有返回目标日期范围内的数据

各来源按完整结果切换。项目当前不会自动把东方财富和新浪的局部时间窗口拼接为一份更长的结果。

新浪返回的数据没有成交额，因此 `amount` 保持为空。`vol` 仍然表示成交量，两者不会互相替代。

## 2026-08-25 现场记录

以下结果来自 `510050.SH`，测试时间为 2026-08-25 上午 A 股交易时段内。AKShare 版本为 `1.18.94`。

### 东方财富与 AKShare

长周期测试把请求起点放到约 8000 个自然日前，使用 `fund_etf_hist_min_em`。现场返回如下：

| 周期 | 行数 | 最早时间 | 最晚时间 | 覆盖交易日 |
| --- | ---: | --- | --- | ---: |
| `1` 分钟 | 1010 | 2026-08-19 09:30 | 2026-08-25 10:15 | 5 |
| `5` 分钟 | 1497 | 2026-07-13 09:35 | 2026-08-25 10:15 | 32 |
| `15` 分钟 | 499 | 2026-07-13 09:45 | 2026-08-25 10:15 | 32 |
| `30` 分钟 | 250 | 2026-07-13 10:00 | 2026-08-25 10:30 | 32 |
| `60` 分钟 | 125 | 2026-07-13 10:30 | 2026-08-25 10:30 | 32 |

`1` 分钟最近 5 个交易日的限制与 AKShare 对该接口的说明一致。`5/15/30/60` 分钟没有固定历史长度承诺，因此 2026-07-13 这个起点只能视为当天的接口行为。

### 新浪历史分钟接口

项目通过 `CN_MarketData.getKLineData` 请求新浪历史分钟 K 线。该接口按返回根数提供最近数据，不接收任意起止日期。

现场对 `510050.SH` 的结果如下：

| 周期 | 行数 | 最早时间 | 最晚时间 |
| --- | ---: | --- | --- |
| `5` 分钟 | 5010 | 2026-03-24 14:20 | 2026-08-25 10:15 |
| `15` 分钟 | 5004 | 2025-05-15 11:30 | 2026-08-25 10:15 |
| `30` 分钟 | 5003 | 2024-01-22 15:00 | 2026-08-25 10:30 |
| `60` 分钟 | 3900 | 2022-08-16 11:30 | 2026-08-25 10:30 |

项目请求较大的 `datalen`，现场返回量仍大约停在 5000 根附近。周期越长，同样数量的 K 线可以覆盖更长时间，因此 30 分钟和 60 分钟在这次观测中能追溯得更早。

当前 CLI 没有单独选择新浪或东方财富的 `--source` 参数。默认回退链路只在前一层失败或返回空结果时继续向后尝试，也不会为了补更早历史主动拼接新浪数据。因此上表用于说明各公开接口的现场能力，不能直接推导某条 CLI 命令一定会覆盖到对应最早日期。

## 日期和空数据

CLI 使用 `YYYYMMDD` 日期，目标范围按自然日生成。周末和节假日通常没有行情，对应日期会记为 `empty`。

对于超出上游历史范围的日期，可能出现以下结果：

- 行情源返回空表
- 返回结果只覆盖请求范围中的一部分交易日
- `fetch_symbol_range()` 把缺少行的目标日期记为 `empty`
- 整批任务没有写入或跳过任何分区时，CLI 以退出码 `3` 结束

因此命令成功执行只能说明任务流程完成。研究数据是否完整，还需要检查实际交易日分区。

## ETF 历史范围

`--universe cn-etf` 默认获取当前沪深 ETF 集合。使用 `--as-of YYYYMMDD` 时，项目会查询对应日期的历史 ETF 快照。

历史快照可以降低直接使用当前 ETF 列表回填历史数据造成的幸存者偏差。当前项目没有稳定、对称的 `list_date` 和 `delist_date` 元数据源，因此需要严格处理上市、退市和更名历史的研究仍应补充独立证券主数据。

## 输出字段

每个交易日分区使用以下固定字段：

| 字段 | 含义 |
| --- | --- |
| `ts_code` | 标准化 ETF 代码，例如 `512880.SH` |
| `trade_time` | 分钟时间戳 |
| `open` | 开盘价 |
| `high` | 最高价 |
| `low` | 最低价 |
| `close` | 收盘价 |
| `vol` | 成交量 |
| `amount` | 成交额，新浪数据为空 |

目录结构为：

```text
<out>/<ts_code>/trade_date=YYYYMMDD/part.parquet
```

## 长期归档建议

需要多年稳定分钟数据时，更可靠的做法是持续增量归档：

1. 每个交易日抓取新数据
2. 按 `trade_date` 保存本地分区
3. 定期检查缺失交易日和异常空值
4. 谨慎覆盖已经验证的历史分区
5. 对研究数据集保存版本或快照信息

`1` 分钟数据尤其需要持续归档。超过上游保留窗口后，当前公开接口通常无法补回已经过期的分钟记录。

## 重新做现场检查

可以用健康检查确认当前默认链路是否仍然可用：

```bash
uv run etf-min-check \
  --symbol 510050.SH \
  --period 30 \
  --lookback-days 8000
```

输出会给出实际返回的最早和最晚时间，以及核心字段和成交额的空值数量。定期记录这些结果，比在业务代码里写死固定可用年限更可靠。
